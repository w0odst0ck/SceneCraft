# GitHub 短剧开发平台调研

> 调研日期：2026-11-26 · 数据源：GitHub API（star/fork/许可/目录结构/README 实测）
> 目的：为 SceneCraft 之后的方向选择提供依据 —— **先跑现成的，遇到问题再做插件**

---

## 一、结论先讲（TL;DR）

### 三个关键发现

1. **头部项目都是「平台」，不是「库」** ——前 5 名（1.7k~18k★）全是带前端的完整产品（Web/桌面/Docker），
   **没有一个提供可嵌入的 Python/TS 库**。这意味着：**要么用它们的产品，要么和它们竞争，没有中间路线**。

2. **「开源」水分很大** ——实测目录结构：
   | 项目 | 仓库里有什么 | 判定 |
   |---|---|---|
   | BigBanana（2480★） | **只有 README + docker-compose + 截图**，**零源码** | ❌ **假开源**（只发布镜像） |
   | huobao-drama（17992★） | backend/src + frontend + desktop，**真源码** | ✅ 真开源（但 NC 许可） |
   | aid-studio（1785★） | 6 个 Java 模块 + 前端 + deploy + **MIT** | ✅ 真开源，许可最友好 |

3. **许可会卡死你的路** ——
   - **huobao-drama / BigBanana = CC BY-NC-SA 4.0**（**禁止商用**）
   - **aid-studio = MIT**（唯一可商用的头部项目）
   - SceneCraft 自己是 MIT

### 给你的建议（三步）

| 步 | 做什么 | 理由 |
|---|---|---|
| **1** | **先跑 huobao-drama**（零配置，10 分钟出片） | 17.9k★、零配置启动（SQLite + 内置 FFmpeg）、功能最全、真源码。**先看清"好产品长什么样"** |
| **2** | **再跑 aid-studio**（MIT，可商用） | 如果想长期做，这是唯一许可干净的头部选项；Java 栈但 Docker 一键部署 |
| **3** | **不建议跑 BigBanana** | 零源码，只能拉镜像——你无法改、无法学、无法做插件 |

## 三、深度对比：前四名到底差在哪

### 3.1 huobao-drama（17992★）— 事实标准

| 维度 | 情况 |
|---|---|
| **架构** | Nuxt3+Vue3 前端 / Hono+Drizzle+Mastra Agents 后端 / Electron 桌面 |
| **数据库** | SQLite 单文件（**零安装**） |
| **FFmpeg** | **npm 内置二进制**（`ffmpeg-static`，开箱即用） |
| **启动** | `cd backend && npm install && npm run dev` —— **你自己的机器就能跑** |
| **Agent** | 4 个 Mastra Agent：script_rewriter / extractor / storyboard_breaker / prompt_generator |
| **模型** | 文本 OpenAI/Gemini · 图片 OpenAI/Gemini/火山 · 视频 **Seedance 2.0 / MiniMax H3 / Wan 3.0** |
| **角色管理** | ✅ 角色形象生成 + 批量生成 + 上传管理 |
| **中文** | ✅ 原生中文界面 + AI 内容语言可设 |
| **致命限制** | **CC BY-NC-SA 4.0 = 禁止商用**；且**不支持本地模型**（全走 API） |

**对你的价值**：**用它做"标杆"** —— 看清一个 18k★ 的产品长什么样、流程怎么设计、UI 怎么组织。

### 3.2 BigBanana（2480★）— 最好的产品定位，最差的开源

**它的产品思路完全命中你说过的痛点**（README 原文）：
> "AI 漫剧最致命的痛点不是画质、不是配音，而是**角色一致性**——换个镜头就变脸，观众瞬间出戏。"
> "采用 Script-to-Asset-to-Keyframe：**先有演员和片场，再开机**"
> "定妆照 + 衣橱系统 + 上下文感知，**三重约束锁定形象**"

这正是你 11-26 上午问我的「角色一致性插件」——**人家已经做了，而且做成产品了**。

**但致命问题**：仓库里**只有 README + docker-compose + 截图**，没有一行源码。
- 你只能拉 Docker 镜像用
- 无法学它的实现
- **无法做插件**（没有扩展点）
- 且**同样 CC BY-NC-SA 禁商用**

**结论**：可以**拉镜像体验产品思路**，但别指望在它上面开发。

### 3.3 aid-studio（1785★，MIT）— 唯一许可干净的头部

| 维度 | 情况 |
|---|---|
| 架构 | Java 多模块（aid-admin/business/common/consumer/interface）+ 前端 |
| 功能 | 流程化创作 · **无限画布** · **导演台**（机位/构图/运镜）· **3D 预演台** · 管理后台 |
| 部署 | **Docker + systemd**，后台可配供应商/计费/并发 |
| 许可 | **MIT** ✅ 可商用、可改、可分发 |
| 短板 | Java 栈（你是 Python 背景）；体量 87MB；11-25 刚更新 |

**对你的价值**：如果决定长期做这件事，**这是唯一能合法商用的地基**。

### 3.4 xhongc/ai_story（2122★，Python）— 技术栈最接近你

- Python 3.11 + Docker（amd64/arm64）
- 文案 → 分镜 → 图片 → 运镜 → 视频
- 有赞助商（MiniMax H3 API / 5gtoken），说明已产品化
- 许可未标注（**风险**）

## 五、三个可行方向

### 方向 A：用 huobao-drama 作为产品壳，把 SceneCraft 当"引擎插件"

```
huobao-drama（UI + 任务流 + 模型管理）
   ↓ 缺什么
   缺：契约化产物 / 分批生成 / 版权素材库
   ↓ 你有
SceneCraft 的 5 个包
```

**可行性**：中。huobao 是 TS，你是 Python → 必须走 HTTP 服务或重写。
**风险**：CC BY-NC-SA 禁商用（自己用没问题）。

### 方向 B：用 aid-studio（MIT）作地基，贡献 Python 侧能力

**可行性**：中低（Java 栈）。
**优势**：许可干净，可商用；有无限画布/导演台/3D 预演（你不可能自己做这些）。

### 方向 C（**推荐**）：先跑，再决定

按用户 11-26 的判断：
```
跑 huobao-drama（10 分钟，零配置）
  → 用它做一条真片
  → 记录：哪里好、哪里差、缺什么
  → 如果发现"它缺的东西正好我有" → 才做插件
```

**为什么这个顺序对**：
- 你已经花了 4 个半月做架构，**缺的是"好产品长什么样"的实感**
- 跑一遍 huobao，你会立刻知道：UI 该怎么做、流程该怎么排、用户在哪一步会卡
- 而且**不需要写一行代码**

## 六、立即可执行的动作

```bash
# 方案 A：跑 huobao-drama（零配置，推荐先做）
git clone https://github.com/chatfire-AI/huobao-drama.git
cd huobao-drama/backend && npm install
cd ../frontend && npm install
# 终端1: cd backend && npm run dev      → :5679
# 终端2: cd frontend && npm run dev     → :3013

# 方案 B：跑 aid-studio（MIT，Docker）
# 见其 deploy/ 目录

# 方案 C：跑 wind-comic（零密钥 mock）
MOCK_ENGINES=1 PIPELINE_QUEUE=1 npm run build && npm start

# 方案 D：跑 openshorts（本地优先）
npx openshorts    # 需要 ffmpeg（本机缺，需先装）
```

**前置**：本机**没有 ffmpeg**（huobao 用 npm 内置的，不影响；openshorts 需要单独装）。

## 七、我的判断（直说）

1. **你在架构上已经不落后了** —— 契约/分批/素材库这三样，前 5 名里没有一个有。
2. **你落后的是「产品化」** —— UI、角色管理、音频、模型接入。这些**不是靠再写架构能补的**。
3. **所以正确顺序是**：先用别人的产品（huobao/aid-studio）把「一条好片」跑通，
   看清差距后再决定：是**补产品化**，还是**把架构能力做成插件**卖给这些平台。
4. **最不该做的**：再写一个自己的平台（第 6 个 1.7k★ 项目不会比前 5 个更好）。
